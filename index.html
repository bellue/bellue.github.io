01

팀스페이스 생성/조회

왜 중요했나

팀스페이스는 체크리스트, 팀 룰, GitHub 연동의 기준 데이터입니다. 첫 생성이 틀리면 이후 기능이 모두 잘못된 팀을 기준으로 동작합니다.

검토한 선택지

매칭 결과를 그대로 저장하는 방식과 서버에서 4인 팀, HOST 1명, 중복 사용자, ACTIVE 팀 중복 소속을 검증하는 방식을 비교했습니다.

트레이드오프

생성 로직은 복잡해졌지만, 잘못된 팀 데이터가 후속 기능으로 전파되는 비용을 줄였습니다.

검증 자료

ProjectGroupServiceTest에서 팀원 수, HOST 수, 중복 사용자, ACTIVE 팀 중복 소속, 종료 동의 케이스를 테스트했습니다.

02

체크리스트 API

왜 중요했나

체크리스트는 팀의 작업 기록입니다. 팀원이 아닌 사용자를 담당자로 지정하거나 종료된 팀에서 수정되면 기록 신뢰도가 떨어집니다.

검토한 선택지

프론트엔드 검증에 맡기는 방식과 서비스 레이어에서 멤버십, 종료 상태, AI 응답 구조를 다시 검증하는 방식을 비교했습니다.

트레이드오프

검증 분기가 늘어났지만, 클라이언트 우회 요청과 Gemini 응답 오류가 저장 데이터로 들어오는 위험을 줄였습니다.

검증 자료

ProjectChecklistServiceTest와 ControllerTest에서 담당자 검증, 종료 상태 쓰기 제한, Gemini JSON 파싱 실패를 확인했습니다.

03

GitHub App / Repository / PR 기여도 연동

왜 중요했나

GitHub 연동은 외부 권한과 내부 팀 데이터를 연결합니다. callback 재사용, 권한 없는 저장소 선택, PR 중복 저장이 모두 데이터 오염으로 이어질 수 있습니다.

검토한 선택지

state를 조회만 하는 방식과 Redis에서 get-and-delete로 1회 소비하는 방식, PR ID를 한 번에 조회하는 방식과 500개 단위 chunk 조회를 비교했습니다.

트레이드오프

검증과 조회 단계는 늘어났지만, replay 가능성, 접근 불가능한 Repository 저장, 큰 IN 쿼리 부담을 줄였습니다.

검증 자료

TeamspaceServiceTest에서 state 소비, 설치 완료 실패 케이스, PR ID chunk 크기 500 이하를 테스트했습니다.

04

팀스페이스 종료 API

왜 중요했나

팀스페이스 종료는 체크리스트와 팀 룰의 쓰기 제한으로 이어지는 상태 전이입니다. 한 명의 요청만으로 종료되면 팀 합의가 깨집니다.

검토한 선택지

HOST 단독 종료, 과반 동의, 4인 전원 동의 중에서 팀 프로젝트 종료라는 도메인 특성을 기준으로 4/4 동의를 선택했습니다.

트레이드오프

종료까지 필요한 액션 수는 늘었지만, 일방 종료를 막고 상태 전이를 비관적 락으로 보호했습니다.

검증 자료

ProjectGroupServiceTest에서 동의 4건이면 FINISHED, 2건이면 ACTIVE 유지, 이미 종료된 팀의 재요청 실패를 확인했습니다.

05

팀 룰 API

왜 중요했나

팀 룰은 회의 시간, PR 규칙, 역할 분담처럼 팀 운영 기준을 담습니다. 동시에 수정될 때 마지막 저장이 이전 내용을 덮어쓰면 합의 내용이 사라집니다.

검토한 선택지

마지막 저장 우선, 비관적 락, version 기반 낙관적 락을 비교했습니다. 읽기와 간헐적 수정이 많은 문서 성격을 보고 낙관적 락을 선택했습니다.

트레이드오프

충돌 시 사용자가 다시 저장해야 하지만, 평소에는 잠금 대기 없이 조회와 수정을 처리할 수 있습니다.

검증 자료

TeamRuleServiceTest와 ControllerTest에서 기본 룰 생성, version 불일치 충돌, 종료 팀 수정 차단을 확인했습니다.

06

테스트 / CI / 마이그레이션

왜 중요했나

로컬 H2 테스트만 통과해도 MySQL 문법이나 Flyway 마이그레이션에서 실패할 수 있습니다. 배포 전 스키마 검증 경로가 필요했습니다.

검토한 선택지

모든 테스트를 MySQL로 돌리는 방식과 기본 H2 테스트, 필요 시 MySQL/Flyway 검증을 켜는 방식을 비교했습니다.

트레이드오프

기본 테스트 속도는 유지하고, DB 의존 검증은 RUN_DB_TESTS=true일 때만 실행되도록 분리했습니다.

검증 자료

README 실행 절차, TeamPoApplicationFlywayTests, feature 패키지 기준 29개 테스트 파일과 118개 @Test 케이스로 회귀를 확인했습니다.
